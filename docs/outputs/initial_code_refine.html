2  AdminOptim.java — Adjacency-list refactor

DONE
src/admin/AdminOptim.java

Motivation

The previous implementation stored the social graph as a dense double[N][N] matrix and iterated the full N-agent array to find followers of each posting agent — an O(N) scan per post per step, giving O(N·posts·steps) overall. With N = 1000 and 40 000 steps this compounds to roughly 40 million unnecessary checks per simulation run.

New representation

private Set<Integer>[] followees;  // followees[i] = agents i follows
private Set<Integer>[] followers;  // followers[j] = agents that follow j

Both sets are built once from the initial W matrix in the constructor (O(N²) one-time cost) and updated incrementally in updateAdjacencyMatrix() in O(1) per edge change.

On-demand matrix generation

/** Only called every 5000 steps for GEXF export / degree / clustering. */
public double[][] getAdjacencyMatrix() {
    double[][] matrix = new double[n][n];
    for (int i = 0; i < n; i++)
        for (int j : followees[i])
            matrix[i][j] = 1.0;
    return matrix;
}

Code paths that require the full matrix (GEXF export, degree CSV, clustering coefficients) call getAdjacencyMatrix() locally at the 5 000-step checkpoint — not every step.

O(edges) disagreement computation

public double computeDisagreement(Agent[] agentSet) {
    double sum = 0.0;  int edgeCount = 0;
    for (int i = 0; i < n; i++)
        for (int j : followees[i]) {
            double diff = agentSet[i].getOpinion() - agentSet[j].getOpinion();
            sum += diff * diff;  edgeCount++;
        }
    return edgeCount > 0 ? sum / edgeCount : 0.0;
}

This replaces the prior analyzer.computeDisagreement(agentSet, W) which scanned all N² entries. The call site in OpinionDynamics.evolve() was updated accordingly.

Incremental edge update

updateAdjacencyMatrix(userId, followedIds, unfollowedId) now updates both sets and followerNumArray in O(1) using Set.add() / Set.remove(), replacing the previous full-matrix cell write.

double[][] W = admin.getAdjacencyMatrix(); was materialising a full N×N matrix at the start of every simulation step. This line is removed. All per-step logic now uses adjacency sets via admin.getFollowers(agentId).

4.2 — Post and repost distribution: O(N) → O(degree)

// OLD — iterates all N agents
for (Agent otherAgent : agentSet) {
    if (W[otherAgent.getId()][agentId] > 0.00)
        otherAgent.addToPostCash(post);

// NEW — iterates only followers
for (int followerId : admin.getFollowers(agentId)) {

Previously ASChecker.assertionChecker() was called once per agent inside the shuffled-agent loop, re-validating global invariants N times per step. It is now called once after the loop completes, which is both semantically correct (post-step validation) and reduces redundant checks.

5  Writer.java — Batch CSV output (1 000 steps/file)

DONE
src/writer/Writer.java

Motivation

The prior design opened and closed a new file for every simulation step, producing 40 000 separate CSVs per run per output type. This creates excessive filesystem pressure and makes notebook aggregation slow (40 000 pd.read_csv calls).

New batch design

Three StringBuilder buffers (metricsBuf, postsBuf, opinionBuf) accumulate rows. When the buffer reaches BATCH_SIZE = 1000 steps, a private flushBatch() method writes three files and resets the buffers: 

metrics/result_0_999.csv
posts/post_result_0_999.csv
opinion/opinion_result_0_999.csv

metrics/result_1000_1999.csv
...
metrics/result_39000_39999.csv

Each batch file is a standard multi-row CSV with a header row and one data row per step. The public flush() method handles the final partial batch at end-of-simulation.

Dead code removed

  • private double feedVar — scalar field never set from outside; its "feedVar" RESULT_LIST key was also absent, making it completely inert. Removed along with setFeedVar().
  • handleSingleMetric() renamed to appendSingleMetric() to reflect that it appends to a StringBuilder argument rather than writing to a file.

All four functions previously used a step_file_map approach: they extracted the step number from the single-step filename (post_result_123.csv), read the single-row file, and took df.iloc[0]. The new pattern: 

# Read all batch files and concatenate
dfs = []
for f in glob.glob(os.path.join(dir, "post_result_*.csv")):
    try:
        df_temp = pd.read_csv(f)
        if not df_temp.empty: dfs.append(df_temp)
    except: pass
all_df = pd.concat(dfs).sort_values("step").reset_index(drop=True)
for _, row in all_df.iterrows():
    step = int(row["step"])
    ...

The MAX_INDEX filter is applied after concatenation via boolean masking rather than inside the file-selection loop, which is both cleaner and correct for batch files that span a step range.

The glob pattern post_result_*.csv matches both the legacy single-step names and the new range names (post_result_0_999.csv), ensuring backward compatibility with any existing data.

7  Deferred items (noted for future reports)

DEFERRED
Note: The following issues were identified in the initial review but are intentionally left unchanged at the user's request. They should be flagged in any future model report or sensitivity analysis.

7.1 — postProb and useProb are effectively frozen

In Const.java: 

public static final double INITIAL_PU = 0.0025;
public static final double MAX_PU = INITIAL_PU;   // = 0.0025
public static final double MIN_PU = INITIAL_PU;   // = 0.0025

Because MAX_PU == MIN_PU == INITIAL_PU, the clamping in Agent.updateMyself() pins useProb to exactly 0.0025 regardless of comfort-rate feedback. The adaptive engagement mechanism is mathematically present but numerically inert. The same applies to postProb where MAX_PP = 1.0 and MIN_PP = 0.05 leave some room, but the initial value of 0.10 and a zero post cost (POST_COST = 0.0) mean the effective dynamics depend entirely on the multiplicative updates in updateMyself().

7.2 — Comfort threshold uses MINIMUM_BC, not dynamic bc

In Agent.updateMyself(): 

if (Math.abs(post.getPostOpinion() - this.opinion) < Const.MINIMUM_BC) {
    comfortPostNum++;
}

This uses the global floor MINIMUM_BC = 0.2 rather than the agent's current dynamic this.bc, which can decay below 0.2 via bc *= BC_DEC_RATE (note: the clamp at line 313 uses a Math.min(Const.MINIMUM_BC, 1.0) which is always MINIMUM_BC, effectively never raising bc — only the decay acts). As a result, the comfort rate is measured against a fixed window while the opinion update uses a potentially narrower one, creating an asymmetry in the model's micro-logic.
